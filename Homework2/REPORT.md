## 一、專案目標

設計並實作一套具備完整校務流程的網頁系統，模擬金門大學的日常教學行政工作。系統需要同時服務三種身分（學生、教師、教職員），並在瀏覽器與伺服器之間傳遞真實的資料互動，而非單純的靜態展示。

實作時特別重視三件事：

1. **不依賴第三方套件**：全程只使用 Node.js 內建模組，理解 HTTP 與加密的實際行為。
2. **領域規則集中在服務層**：選課、成績、繳費的規則不寫在路由裡，而是集中在可單獨測試的函式中。
3. **安全性**：密碼、工作階段、CSRF 與授權都要有實際的處理，而不是僅僅在前端隱藏按鈕。

## 二、系統架構

系統採用三層架構，各層職責分明：

```
請求 (node:http)
   ↓
路由層  src/app.ts          路徑比對、認證、CSRF、錯誤處理
   ↓
服務層  src/services/*.ts   領域規則：衝堂、先修、學分、成績、繳費
   ↓
儲存層  src/db/store.ts     記憶體資料 + JSON 原子式寫入
```

### 2.1 路由層

`Router` 支援 `:param` 形式的路徑參數，並記錄每條路由允許的角色。請求進來時依序完成：

1. 從 Cookie 取出工作階段（沒有就發給訪客一個，供取得 CSRF token）
2. 比對路由；找不到路徑回 404、方法不符回 405
3. 檢查角色
4. 執行處理器，例外交給統一錯誤處理

### 2.2 服務層

領域規則集中在 `src/services/`，例如：

```typescript
export function enroll(db, student, courseId, options): EnrollResult {
  // 學期 → 開放選課 → 重複 → 先修 → 衝堂 → 學分上限 → 名額／候補
}
```

這樣做的好處是規則可以被獨立測試，路由只負責「取出參數、呼叫規則、把結果畫出來」，不會把業務邏輯散落在數十個 `router.post()` 之中。

### 2.3 儲存層

資料放在單一 JSON 檔案中。寫入流程是「序列化 → 寫入暫存檔 → `fs.renameSync` 覆蓋」，因為 `rename` 在同一個檔案系統中是原子操作，可以避免寫到一半當機導致資料損毀。所有變更都經過 `store.mutate()`，確保「驗證 → 套用 → 寫檔」的順序一致。

## 三、核心功能設計

### 3.1 登入與工作階段

密碼以 `scrypt` 加隨機 salt 雜湊，比對時使用 `timingSafeEqual` 避免時間差洩漏。工作階段存放在伺服器記憶體中，Cookie 只帶隨機 token，並設定 `HttpOnly` 與 `SameSite=Lax`。

登入成功後會**廢棄原本訪客的工作階段**並發給新的，這是防止 session fixation 的標準做法；同時清除記錄的登入失敗次數。

針對密碼暴力破解，同一帳號連續失敗達 `LOGIN_MAX_FAILURES` 次後暫時鎖定 `LOGIN_LOCKOUT_MS`。

### 3.2 選課系統

選課規則依序檢查，任何一項不符就拋出 409（Conflict），並在畫面上顯示具體原因：

| 規則 | 說明 |
|------|------|
| 學期 | 只能選目前學期的課程 |
| 開放狀態 | 課程需開放選課 |
| 重複 | 已選或已在候補名單中都不能再選 |
| 先修條件 | 先修課程需有已公布的及格成績 |
| 衝堂 | 比對每週上課的節次區間（含候補中的課程） |
| 學分上限 | 已選學分加上新課學分不得超過上限 |
| 名額 | 額滿時排入候補，退選後自動依序遞補 |

其中「衝堂」的判斷是這樣做的：把課程的 `sessions`（星期 + 起始節次）搭配 `periods`（每次上幾節）展開成節次區間，只要與已選課程的區間重疊就擋下。

### 3.3 成績管理

成績由多個評分項組成（如期中考 50%、期末考 50%），教師可自訂名稱、分數與權重。加權總分落在 0–100 之間，轉換為等第（甲上到丁）後計算 GPA。

**成績登錄與公布是分開的**：教師輸入成績後，學生的 GPA 不會立刻變動，只有當教師將該筆成績標記為「已公布」後，學生的成績單與 GPA 才會更新。這樣可以避免期中成績被同學即時得知。

服務層會同時檢查「操作者是不是這門課的教師（或教職員）」與「這位學生有沒有選這門課」。

### 3.4 繳費系統

繳費單包含多個項目（學費、雜費、電腦網路使用費、平安保險費）與學費減免。每個項目各自記錄是否已繳與繳費時間，因此「部分繳費」是自然形成的狀態，不必額外儲存。

線上繳費要求金額必須**剛好對應依序沖銷前 n 個完整項目的合計**，介面以選單列出所有合法金額。如此可避免「收了錢卻沒有任何項目被沖銷」的資料不一致，也讓使用者不可能填出無效金額。

### 3.5 校園公告

公告支援分類、關鍵字搜尋、置頂與刪除，只有教職員能發布。

## 四、安全設計

| 項目 | 作法 |
|------|------|
| 密碼 | `scrypt` + 隨機 salt，不存明文 |
| 工作階段 | 隨機 token 於記憶體，Cookie 設 `HttpOnly`、`SameSite=Lax` |
| Session fixation | 登入後換發新工作階段 |
| CSRF | 每個表單內嵌 token，以固定時間比對驗證 |
| XSS | 使用者輸入在輸出前一律 `escapeHtml` |
| 授權 | 路由宣告角色 + 服務層檢查資源擁有者 |
| 登入爆破 | 失敗次數鎖定 |
| 開放轉向 | `next` 只接受以單一 `/` 開頭的站內路徑 |
| 資料寫入 | 原子式寫檔，避免中斷造成資料損毀 |

有一個細節值得一提：CSRF token 的比對先檢查長度，再用迴圈累積每個位元組的 XOR 差異，最後判斷差異是否為 0。雖然在本專案的規模下差異不大，但這是避免「回應時間洩漏 token 內容」的標準寫法。

## 五、遇到的問題與解決方式

### 5.1 選課規則的檢查順序

一開始把「衝堂」判斷放在「先修條件」之前，導致某些學生看到的是衝堂訊息而不是真正缺少先修的訊息。調整順序為「學期 → 開放 → 重複 → 先修 → 衝堂 → 學分 → 名額」，讓使用者依序處理問題，也讓錯誤訊息的原因由根本開始。

### 5.2 成績外洩

原本 GPA 計算直接統計所有成績紀錄，導致教師尚未公布的成績會反映在學生的 GPA 上。修正方式是讓 `gpaOf()` 與 `cumulativeGpa()` 只計算 `published` 為真的紀錄，並補上測試驗證公布前後的差異。

### 5.3 繳費金額驗證

第一版的繳費邏輯允許輸入任意金額（只要是 100 的倍數），但「已繳」狀態是記在項目上的，因此輸入 150 元時會產生一筆付款紀錄卻沒有任何項目被沖銷。修正為只接受「依序沖銷前 n 個完整項目的合計」，並由 `acceptableAmounts()` 提供合法金額清單給介面。

### 5.4 教職員成績權限

原本 `rosterOf()` 只允許授課教師查看名單，但路由又宣告管理員可用，導致管理員進入成績頁會收到 403。修正為在服務層明確區分兩種身分：教師限本人開的課，教職員可查閱任何班級。

## 六、測試

以 `node:test` 撰寫 44 個測試，全部通過：

| 測試檔 | 內容 |
|--------|------|
| `auth.test.ts` | 登入、CSRF、角色權限、登出 |
| `enrollment.test.ts` | 選課成功、重複、衝堂、先修、學分上限、候補遞補 |
| `grades.test.ts` | 成績輸入驗證、公布後 GPA 更新、未公布成績不外洩 |
| `fees.test.ts` | 繳費成功、金額驗證、越權繳費、繳清後限制 |

測試透過實際啟動 HTTP 伺服器、以 `fetch` 送出請求並維護 Cookie 完成，屬於端對端測試，能同時驗證路由、服務與頁面渲染。每一個測試都有獨立的暫存資料檔與隨機埠號，彼此不會干擾。

## 七、改進方向

1. **資料庫**：改用 SQLite 或真正的資料庫，取代整份 JSON 載入記憶體的做法。
2. **課程時間**：目前一週只安排單一時段，若允許同課程多個時段，`sessions` 的處理需再調整。
3. **成績計算**：加入補考、棄修與學期重修的規則。
4. **通知**：候補遞補與成績公布時，以電子郵件或站內通知提醒學生。
5. **無障礙**：為表格與表單補上更完整的鍵盤操作與閱讀器標記。
